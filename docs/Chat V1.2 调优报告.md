# Chat V1.2 调优报告

> 调优报告完成时间：2026-08-07 18:57 CST。
>
> 本报告记录单机、回环 TCP、约一分钟混合负载下的实测结果，不等同于生产环境容量承诺。

## 一、调优目标与最终结果

本轮目标不是只让 10000 个客户端保持连接，而是让 10000 个客户端登录后持续执行真实的混合动作，同时完整接收和解码世界频道批量消息。最终配置为 8 个对等接收者分片 Worker，每个 Worker 按 `80ms` 或 `256` 条世界消息组批。

最终 10000 客户端创建耗时 17.175258 秒。约一分钟内，服务端在线角色、世界频道成员和 `role_server` 始终都是 10000；Role 邮箱总量为 10、9、0、1，单个 Role 最大不超过 1；8 个 Worker 邮箱始终为 0。服务端内存从 169.179 MiB 增长到 217.184 MiB，没有出现过载时的队列和内存单调失控。

客户端继续完整拆解 `2010` 内的每一条 `2009`，没有使用跳过消息或简化解包的压测专用路径。客户端邮箱总量为 32、20、24、13，单客户端最大始终为 1；最终内存约 2046.501 MiB。测试结束后服务端和客户端 VM 均已关闭。

## 二、测试节点与运行方式

本次测试使用 1 台物理机和 2 个独立 BEAM VM：

| 运行单元 | 数量 | 作用 |
|---|---:|---|
| 服务端 BEAM VM | 1 | 启动一个 Chat OTP Application、8 个世界 Worker 和 10000 个动态 `role_server` |
| 客户端 BEAM VM | 1 | 由一个 `chat_client_sup` 启动并监督 10000 个 `chat_client` |
| Erlang 分布式节点 | 0 | 启动脚本没有使用 `-name` 或 `-sname`，两个 VM 都显示为 `nonode@nohost` |
| TCP 连接 | 10000 | 客户端 VM 通过本机 `127.0.0.1:5555` 连接服务端 VM |

因此从部署角度可以说是“1 个服务节点加 1 个压测 VM”，但不是 8 个服务节点。8 个 `world_broadcast_worker` 只是同一个服务端 VM 内的 8 个 Erlang 进程。

主要启动和观察命令为：

```erlang
timer:tc(chat_load_test, start, [1, 10000]).
chat_metrics:snapshot().
```

最终样本中，服务端有 10004 个 Port、10064 个进程，客户端有 10004 个 Port、10042 个进程；测试 VM 使用 16 个在线 Scheduler。

## 三、每个客户端的行为和通信量

每个普通客户端登录成功后，每隔 3 秒随机执行一次动作。按长期理论平均值计算：

| 动作 | 概率 | 单客户端平均发送 | 10000 客户端平均请求量 |
|---|---:|---:|---:|
| 发送 `main` | 40% | 约 0.133 条/秒 | 约 1333 条/秒 |
| 发送私聊 | 40% | 约 0.133 条/秒 | 约 1333 条/秒 |
| 加入公共频道 | 10% | 约 0.033 条/秒 | 约 333 条/秒 |
| 退出公共频道 | 10% | 约 0.033 条/秒 | 约 333 条/秒 |
| 合计 | 100% | 约 0.333 个请求/秒 | 约 3333 个请求/秒 |

所有客户端都属于 `main`，所以约 1333 条世界消息/秒会广播给全部 10000 人：

- 每个客户端理论上每秒收到约 1333 条世界频道逻辑消息。
- 服务端理论上每秒处理约 1333 万次世界消息逻辑接收。
- `80ms` 时间窗下，每个客户端平均每秒接收约 12.5 个 `2010` 批量 Packet，每批约包含 107 条 `2009`。
- 每个客户端还会收到约 0.333 个业务结果/秒；在目标均匀且全部在线时，平均收到约 0.133 条私聊推送/秒。

这些数字是根据随机比例计算的理论平均值，不是端到端累计计数。没有可用私聊目标、可加入频道或可退出频道时，客户端会退化为发送 `main`，因此实际世界消息量可能略高；所有客户端也使用同一个 3 秒间隔，代码没有人为错峰，瞬时流量不会完全均匀。

## 四、世界频道并发广播方案

V1.1 已经证明 10000 个静默连接没有问题，但原始广播会为每条世界消息向每个 Role 投递一个邮箱消息。300 个发送者时，Role 队列和内存持续增长，说明瓶颈不是连接数，而是世界频道的全量 fan-out、Role 邮箱和 Socket 发送。

V1.2 最终处理链路如下：

```text
发送方 role_server
  -> 校验 main 成员和 8 个 Worker
  -> 编码一次 2009，并 cast 给全部 8 个 Worker
  -> 每个 Worker 按 80ms/256 条独立生成 2010
  -> 每个 Worker 只遍历自己的约 1/8 成员 ETS
  -> 每个 Role 只收到所属 Worker 的一个批量 cast
  -> role_server 对该批次调用一次 gen_tcp:send/2
```

RoleId 通过 `phash2(RoleId, 8) + 1` 唯一落入一张成员 ETS，因此没有重复接收。世界消息仍然发给所有在线成员，但批处理把理论上的约 1333 万次 Role cast 和 Socket 发送，降低为约 12.5 批/秒乘 10000 Role，即约 12.5 万次批量发送/秒。单批平均约 107 条消息，所以邮箱消息和 Socket 调用大约减少两个数量级。

该方案没有减少总逻辑消息量和网络内容，只减少重复遍历、邮箱信号和 Socket 调用。8 个 Worker 会分别编码自己的 `2010`；同一发送者到同一 Worker 的顺序保留，不同发送者之间不承诺全局统一顺序。

`2008 success` 表示发送者已经通过成员校验、发布时 8 个 Worker 都存在，并已发出异步 cast，不表示所有接收者已经收到。Worker 在刷批前异常时，该分片尚未发送的内存消息可能丢失。

## 五、调优过程与效果

| 阶段 | 结果 | 主要结论 |
|---|---|---|
| V1.1 无协议批量 | 10000 静默连接通过；200 个发送者观察期通过；300 个发送者两次失败 | 连接不是瓶颈，逐消息全量 fan-out 会压垮 Role 下游 |
| 单个全局 Collector 批量 | 5000、6500 通过；8000 时单个 Worker 队列持续增长 | 全局 Collector 成为串行瓶颈 |
| 8 个对等分片，`20ms/64` | 5000、6500 通过；8000 时 Role 队列快速增长，Worker 接近 0 | Worker 已不堵，批次仍太频繁，瓶颈转到 Role/Socket |
| 8 个对等分片，`100ms/256` | 8000、9000、10000 均通过约一分钟 | 批量发送次数足够低，可以达到目标 |
| 8 个对等分片，`80ms/256` | 10000 通过约一分钟 | 在减少 20ms 最大等待后仍保持稳定，选为最终参数 |

最终 `80ms/256` 的 10000 客户端样本如下：

| 样本 | Role 队列总量/最大 | Worker 队列总量/最大 | 服务端内存 | 客户端队列总量/最大 | 客户端内存 |
|---|---:|---:|---:|---:|---:|
| 首次 | 10 / 1 | 0 / 0 | 169.179 MiB | 32 / 1 | 1776.423 MiB |
| 约 15～20 秒 | 9 / 1 | 0 / 0 | 193.609 MiB | 20 / 1 | 1948.164 MiB |
| 约 30 秒 | 0 / 0 | 0 / 0 | 206.090 MiB | 24 / 1 | 2049.442 MiB |
| 约 60 秒 | 1 / 1 | 0 / 0 | 217.184 MiB | 13 / 1 | 2046.501 MiB |

队列始终处于个位数或几十条的瞬时波动，没有单向增长；每个进程的最大队列不超过 1。与 `20ms/64` 的 8000 失败轮相比，Role 队列不再从几十万增长到几百万，证明扩大时间批次直接缓解了 Socket 调用压力。

## 六、客户端退出和异常断线

每个 TCP 连接由独立 `role_server` 负责。正常关闭时，服务端收到 `{tcp_closed, Socket}`，对应 `role_server` 结束；`role_online_server` 和各频道进程监控该 Role，收到 `DOWN` 后删除 `online_roles`、公共频道成员和所属世界成员 ETS 记录。

连接出现可检测错误时，服务端收到 `{tcp_error, Socket, Reason}` 并结束 Role。高负载下客户端 VM 突然整体退出时，部分 `role_server` 可能先处理到待发送批次，`gen_tcp:send/2` 返回 `closed` 或 `einval`，这些 Role 会以 `tcp_send_failed` 退出并产生较多 Supervisor 日志；监控清理最终仍会完成。

当前没有应用层心跳。网线断开但操作系统暂时没有报告 TCP 关闭的“静默断网”，服务端不能立即判断客户端已经离线，只能等待 TCP 错误或后续读写暴露连接异常。

## 八、结论与限制

当前版本已经在本机用 1 个服务端 VM 和 1 个客户端压测 VM，完成 10000 个活跃客户端约一分钟混合负载验证。每个客户端每 3 秒执行一次真实动作，世界频道保持完整广播，客户端完整解包，服务端和客户端邮箱都没有持续积压。

该结果仍有以下边界：

- 测试使用同一台机器和回环 TCP，不能直接外推到真实网络。
- 观察时间约一分钟，还不是小时级或天级稳定性测试。
- 世界频道总数据量仍是 O(发送者数 × 接收者数)，更高人数或更高发送频率仍可能达到单机上限。
- `{active, true}` 没有邮箱背压，超过持续处理能力后仍可能快速积压。
- 异步成功不承诺接收者送达，Worker 刷批前异常可能丢失内存批次。
- 当前没有心跳，静默断网不能立即清理；大批客户端突然退出仍会产生 `tcp_send_failed` 日志噪声。

在本轮“单机 10000 活跃客户端”的目标范围内，`80ms/256` 是已经实测通过、实现简单且延迟可控的最终参数。
